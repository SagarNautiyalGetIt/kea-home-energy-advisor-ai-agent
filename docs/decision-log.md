# Decision log

One line per non-obvious choice, with the date and the reason. Half the MIT report
writes itself out of this file, and future-you stops re-deciding settled things.

Substantial decisions get their own ADR in `docs/adr/`; this is for everything smaller.

| 2026-08-18 | Two-speed models: adopt the shape, skip the second model | The fast/slow pattern assumes a slow reasoning step to hide. ADR-0002 already moved reasoning out of the model — layer 1 is arithmetic and runs in ~1 ms — so the only delay is narration. Revisit for barge-in (Sprint 3) |
| 2026-08-18 | Demo machine = MacBook Pro M4 Pro / 48 GB | Benchmarked both Macs: 2.15× the mini on 4B models, 2.42× on 12B. Mac mini is a genuine backup provided we ship a 4B model |
| 2026-08-18 | Primary model candidate = `qwen3:4b` | 141 ms to first word vs 322 ms for `gemma3:4b` at identical throughput, consistent across both machines. For a phone channel, first-word latency beats raw speed. Apache-2.0 licence is a bonus. **Speed decision only** — Day 6 golden set decides quality |
| 2026-08-18 | PostgreSQL, not SQLite (ADR-0006) | Time-series data, `numeric` for money (float drift is the one bug this product cannot survive), `timestamptz` for NZ daylight saving, and a connection-string path to RDS |
| 2026-08-18 | Local git only — never push this repo anywhere | Standing instruction from Akash. The internship is competitive (other teams bid for the same scenario) and the vaults hold client-adjacent and personal material. `.github/workflows/ci.yml` stays as a file but only runs if pushed, which won't happen. Verified: no remote configured on any vault or repo |
| 2026-08-18 | Illustrative Low Fixed Charge rate 0.34 → 0.36 /kWh | At 0.34 the break-even sat at 30 kWh/day, so LFC looked cheaper for almost every household — the tariff advice would have been wrong for most of the demo. 0.36 puts break-even at 20 kWh/day, matching NZ's LFC regulation (~8,000 kWh/yr). Pinned by a test |
| 2026-08-18 | Demo households defined once, in `app/analytics/fixtures.py` | They had been defined twice — the API served H-A..H-E while the seeder wrote H-JUL..H-TARIFF, so every chat request 404'd. `seed.py` now imports the definition |
| 2026-08-18 | `UsageWindow.median_kwh` is a `cached_property` | The median was recomputed once per reading inside a comprehension in `sustained_overshoot_per_day`, making it quadratic. 26 µs at 31 daily totals, **57 ms at one month of half-hourly intervals** — which is exactly what KEA-32's seeding produces. Now 188 µs. Frozen dataclasses cache fine; `cached_property` writes to `__dict__` directly |
| 2026-08-18 | `get_provider()` is `lru_cache`d | It was building a new provider — and therefore a new `httpx.AsyncClient` and connection pool — on every request, and `last_usage` was per-request state the cost projection (KEA-58) could never aggregate. One provider, one pool, closed in the app lifespan |
| 2026-08-18 | `Settings` fields use `default_factory`, not bare `os.getenv` | A bare `os.getenv` in a dataclass body evaluates **once, at class creation**, so every later `Settings()` returned the environment as it was at import. The Day 6 bake-off (KEA-47) sets `KEA_OLLAMA_MODEL` per run — it would have benchmarked the 4B model three times and recorded three results |
| 2026-08-18 | `/chat/stream` validates `customer_id` before the response starts | It returned **500 with a half-open SSE stream** where `/chat` returned 404 for the same input, because the KeyError was raised after `StreamingResponse` had committed a 200 |
| 2026-08-18 | Empty `FactBundle`s carry caveats | `compare_to_last_year` routes but has no layer 1 path (KEA-69), so the model got an empty bundle with **no constraints at all**. This is the one case layer 3 cannot cover: *"your usage was higher than last winter"* has no numeric token, so the number-checker passes it. Caveats are the only guard until the analytics land |
| 2026-08-18 | Sentence splitting by regex, not `text.split(". ")` | The old split broke `"…, e.g. roughly $24"` into a chunk ending `"e.g."` and then appended a second full stop. ADR-0003 has voice speaking sentence one while sentence two generates, so a bad boundary is **audible** |
| 2026-08-18 | Retry names the rejected tokens | Attempt 2 re-sent a byte-identical prompt at temperature 0.2, which mostly reproduces the identical failure — the model had no way to know what was wrong. It now sees which figures were refused. **Whether this lifts the pass rate is a KEA-46 golden-set question, not a matter of taste** — measure it before claiming it |
| 2026-08-18 | Sprint 2 board card IDs renumbered | KEA-35/36/37/38 each named two different cards; KEA-38 was simultaneously done (ADR-0006) and not started (weather normalisation). Day 3 → KEA-64–66, Day 4 → KEA-67–70. Mapping table at the top of `board.md` |
| 2026-09-05 | `rebuild_span.sh` forces the scripted extracts, not just the Spark ones | `spec.py` makes a sealed partition immutable without `--force`, which is right for a re-run and wrong after a span move: every load date that already had a bronze partition kept its OLD parquet, and the loader staged it into a RAW table the script had just truncated. **Truncating RAW is necessary and not sufficient — the stale copy lives one level lower, in the lake.** 6,649 invoice rows, 3,210 duplicate `INV_ID`s, found by a dbt uniqueness test after the loop had run 6h24m |
| 2026-09-05 | The rebuild covers invoice dates outside the reading span | `FROM`/`TO` derive from `LCL_START`/`NZ_SPAN_END` — the dates *readings* exist for — but `invoices` is incremental on `issue_dt`, and invoices fall outside that window at both ends: the nine fixture households bill across 2023-07 → 2024-09, and 125 cohort invoices are issued after the last reading. 153 invoices silently absent from a rebuild that reported no error; every fixture bill vanished and `make assert-serving` failed 8 checks. Asks the source which dates exist rather than looping 762 empty days |
| 2026-09-05 | Snapshot staging in the rebuild verifies itself | `load_all_bronze_to_snowflake` returns 0 when an entity is SKIPPED for want of a partition and 1 only on a real failure, so all twelve snapshots could skip, print "0/12 landed", and `set -e` would see success — dbt then builds every dimension from an empty table. Same lesson as the TRUNCATE above: read the row count back |
| 2026-09-05 | `bill_line`'s sign constraint keys on charge group, not direction alone | The original rule was written when an export credit was the only signed line. A term credit is not export — nothing flowed anywhere — so it carries `direction = 'import'` with a negative amount, and the load rejected all 2,392. The export also had no `CRD` arm, so credits arrived labelled `other`, indistinguishable from a fee; each bug hid the other, and neither reached the live DB's enum, which still had three labels |
| 2026-09-05 | `load_partition_swap` drops months the export no longer carries | It iterates only months present in the staged data, so it can replace a partition and never remove one — while the export applies a 13-month retention window anchored on the data's own max. At one day per tick that leaks one partition a month, slowly enough to look like nothing; moving the span 364 days leaked twelve at once, 8,062,810 rows carrying the old shift alongside correct ones |
| 2026-09-05 | `int_integrity__orphan_streak` deletes resolved subjects in a post-hook | `delete+insert` removes target rows whose key is in the INCOMING batch, and a resolved subject is exactly the one that is not — so its row and frozen `consecutive_misses` survived forever, and an empty orphan set deleted nothing. 493 accounts read "miss 1 of 3" while the live orphan set was empty, quarantining 97% of the cohort. Everything missed by this run is stamped `current_timestamp()`, so anything older than `run_started_at` is resolved by definition — no second copy of the orphan query |
| 2026-09-05 | `gen_audit` rollups are refreshed after every regeneration | They are MATERIALIZED VIEWS and do not follow their base tables. `mv_bills` still held 11,506 rows from the previous span — the same stale figure this repo's own docs were quoting — and three Metabase cards returned nothing. `source_views.sql` already said "re-run after regenerating"; nothing enforced it |
| 2026-09-05 | `KEY_MAP_ICP`'s 494 unmatched rows are left alone | They look like rot and are not: full-refreshing a key map renumbers every live ICP and breaks every id already in the serving store and the fixtures. Stale unused surrogate ids are the price of stable ones. Recorded because the next person will want to tidy them |
| 2026-09-05 | Solar buy-back stays unimplemented until the next regeneration | `plans-and-terms.md` §2 specifies a buy-back rate for all four plans; `02_catalogue.sql` implements none — 0 export components on all 64 KEA plans, `EXPORT_CREDIT` max 0.00 across 12,279 invoices, 50 solar households credited nothing. Found by a Metabase card returning no rows, not by a test. The fix needs catalogue + `gen_billing` + ~6.5 h of rebuild, so it belongs with the next regeneration rather than on its own |
| 2026-09-05 | The recommender imports `analytics/tariff.py` rather than re-rating in SQL | The pricing engine already carries the two rules that make a comparison correct — one banding pass per charge group, a tiling gap rejected at construction — and is unit-tested against rates transcribed from `02_catalogue.sql`. A second implementation in the batch job would drift on the first rate change. Cost of the choice, paid deliberately: `make recommend-plans` mounts `../services/api` read-only and passes `KEA_API_DIR`, because the two trees are separate deployables |
| 2026-09-05 | A tariff rate attaches to a band **label**, not to a band row | `catalogue.tou_band` holds 152 (plan, group, label) groups on the 32 active KEA plans and `tariff_component` carries 136 rates. That is not 16 missing rates — a label appears once per contiguous window, so Vector's off-peak is three rows, and `04_rate_bills.sql` joins the rate on `(charge_scope, band_label)`. Keying on `band_id` bills two thirds of the day at zero; dropping the rate-less labels leaves a hole and `Tariff` refuses to build. The 16 that genuinely have no rate are the `network` `FREE` window on Good Nights and Good Weekends — free power there is free of the lines charge as well |
| 2026-09-05 | `Tariff.loss_factor` — the engine was billing the metered kWh, not the billed kWh | `billing.bill_line` has carried `loss_kwh` and a generated `billed_quantity` since the serving schema was written, and `tariff.py` had no notion of it: energy is billed on **105.11 %** of metered kWh (`04_rate_bills.sql`, import energy per-kWh lines alone). Not a rounding detail in a *comparison* — the uplift is struck on each plan's own energy rate, so 5 % on 25c is not the money 5 % on 14c is, and omitting it shrinks every gap between plans by a different amount. Measured off the issued bills rather than copied from the biller's literal, so the two cannot silently diverge. Modelled-vs-billed went from 1.41 % below to 0.83 % above |
| 2026-09-05 | The recommender prices a 7 × 48 profile, and that is exact rather than an approximation | 499 accounts × 8 plans × a year of half hours is 71 M band lookups. Collapsing readings into (weekday, minute-of-day) buckets loses nothing because `cost_of` is linear in kWh, no band is month-restricted (`tou_band.months` null on all 707 rows), and the daily charges are driven by `days`, which is passed in rather than counted from the readings. 8.9 M readings → 184,464 cells, whole run 10 s. **If a month-restricted band is ever added, this stops being exact** — that is what the null check is guarding |
| 2026-09-05 | `current_annual_cost` is re-rated, never summed from `billing.bill` | `usage_saving` is a difference and is only meaningful if both sides come out of the same engine over the same readings. Billed totals carry mid-period plan versions, estimated reads and rounding per line; subtracting a modelled candidate from a billed actual would attribute all of that to the plan change. Whether the engine reproduces a real bill is item D's question, asked separately |
| 2026-09-05 | Hardship identification is a parent assessment plus signal rows, not one flat table | §E asks for "a per-account signal row with reason codes". Signals alone cannot record *"we looked and this household is fine"* — an absent row means both "assessed, nothing found" and "never assessed", which are opposite answers to a regulator, and `signal_count = 0` is the common result. The parent is also the only sane referent for `kea.alert`: a hardship outreach is triggered by the **set** of codes, so an alert pointing at one signal row would misstate its own trigger. `kea.alert` gained `assessment_id`; `alert_kind = 'hardship_outreach'` previously had nothing to point at |
| 2026-09-05 | `kea.hardship_assessment` carries no score and no severity | Sprint 4's `hardship_risk_score` has `total_score` and a band; this deliberately has neither, because a number invites acting on it and skipping the reasons, and the Consumer Care Obligation is to justify why a **specific** household was flagged. Which combinations of codes warrant outreach is a rule, recorded in `ruleset_version` rather than baked into a weight, so a policy change is legible beside the assessments it did not apply to |
| 2026-09-05 | Medically dependent and vulnerable are flags on the assessment, not signal codes | §E's table lists them alongside the five payment/usage signals; they are not the same kind of thing. Medical dependency is not evidence of financial difficulty — it is a care obligation that changes what the retailer may **do** (no disconnection), and it is often permanent. Filed as sibling rows they inflate every count, and one missed payment plus a medical dependency reads as twice the concern of one missed payment. Copied at assessment time rather than joined, for the same reason `bill_line` stores its rate: the assessment is an append-only record of what was known when the decision was made, and `billing.customer` is a replica the nightly load overwrites in place |
| 2026-09-05 | `hardship_signal_code` is an enum, not the deferred schema's `text` | Five codes, closed vocabulary. A code that can be invented at the call site cannot be counted, cannot be reviewed, and cannot be explained consistently to the household it was applied to — the same argument that gives Stage 7 exactly one `reject_reasons.json`. Adding a code is a migration, which is the correct friction for a vocabulary a regulator may read |
| 2026-09-05 | The plan dashboard spends a third of its panels arguing against itself | It is the first dashboard here that plots an **opinion** rather than an observation: `kea.plan_recommendation` holds what a year *would* have cost on a plan nobody is on, and a counterfactual cannot be checked against an outcome the way a load can be checked against its source. So *How close is second place*, *What was not recommended, and why*, and *Modelled against actually billed* are not an appendix — they are what decides whether the top half means anything. The first of them found that **125 of 499 households sit within $50/yr of their runner-up**, which `rank` alone cannot express |
| 2026-09-05 | Every panel pins one `computed_at`, repeated rather than factored out | `kea.plan_recommendation` is append-only and already holds two generations. A panel missing the pin does not error and does not look wrong — it doubles every count and every dollar, at whatever multiple the next run makes it. A Metabase native question is one statement with nothing to share a CTE with, and a view would put the pin somewhere a reader of the panel cannot see it, so the predicate is copied into all nine |
| 2026-09-05 | `kea.plan_recommendation` stores GST-exclusive dollars, and item A will collide with that | The catalogue's rates are transcribed from Contact's published join journey, which excludes GST, so the engine's output is GST-exclusive and `usage_saving` is ~13% smaller than the same saving on a customer's bill. Ranking is unaffected (GST is a flat 15% on every line) but the figure cannot be quoted as it stands. ⚠️ The term credits are specified **GST-inclusive** (`plans-and-terms.md` §4), so `annual_saving = usage_saving + term_credit` adds two bases the moment `catalogue.term_credit` is populated — fix before item A lands, not after. Found by comparing modelled against `total_charges` and reading −12.18%, which looks exactly like a modelling error and is entirely the GST line |
| 2026-09-05 | `metering.network` has two rows named "Aurora Energy" | AURA (9 active plans, 133 ICPs) and AUNT (1 and 1) are different lines companies with the same display name, so any panel grouping by `network_name` silently merges them. The saving-by-network panel keys on `network_code`. It read correctly before the fix only because AUNT's single household has no recommendation at all — the kind of accident that stops being one |
| 2026-09-08 | Sprint 3 LCL uses three Kea plans; the nine fixtures stay Sprint 2 | The two design screenshots replace the Contact-derived catalogue with Anytime Rate, Time of Use and Free Weekends on Vector / Standard User. LCL ICPs alone feed forecasts, recommendations and hardship decisions; the nine fixtures retain their historical networks and tariffs as regression evidence. A common assumed 8c export rate prevents an unspecified solar term from changing the ranking, and early-exit caps remain presentation-only until an exit lifecycle exists. |
